# Кандидатогенерация для поиска услуг Авито

Для каждого поискового запроса решение отбирает из корпуса 189 тыс. объявлений до 50 кандидатов.
Метрика - Recall@50.

**Результат на платформе: Recall@50 = 0.9020** (метод `ens_all4`)

## 1. Как воспроизвести `answer.csv`

```bash
pip install -r requirements.txt
# положить три parquet-файла в папку data/
```

Есть четыре варианта. **Вариант A даёт ровно тот `answer.csv`, который загружен на платформу**, и работает без GPU.

| Вариант                                                  | Что нужно | Время      | Результат |
|----------------------------------------------------------|---|------------|---|
| A. Готовые модель и артефакты (рекомендуется)            | CPU | ~15–20 мин | тот же `answer.csv`, 0.9020 |
| B. С нуля на своем GPU                                   | NVIDIA GPU + CUDA | ~2 ч       | ≈ 0.90 (см. ниже) |
| C. С нуля, dense на внешнем GPU (например, Google Colab) | браузер + CPU | ~2-2.5 ч   | ≈ 0.90 |
| D. Без dense-модели                                      | CPU | ~1 ч       | ≈ 0.88 |

### A. Готовые модель и артефакты, точное воспроизведение

1. Скачать `models.zip` и `artifacts.zip` по ссылкам выше и распаковать в корень проекта.
   Должно получиться `models/e5-ft/` и `artifacts/` (`emb_*.npy`, `emb_meta.json`, `lgbm*.pkl`).
2. Построить ответ:
   ```bash
   python run.py submit --data data --art artifacts --method ens_all4 --out answer.csv
   ```

Скрипт сам проверит формат (колонки, 50 уникальных id, все id есть в корпусе) и сохранит `answer.csv`.


### B. С нуля на своем GPU

```bash
python train_dense.py --data data --out models/e5-ft                  # дообучение e5, ~20-40 мин на GPU
python embed.py --data data --model models/e5-ft --art artifacts      # эмбеддинги 516 тыс. объявлений
python run.py val --data data --art artifacts                         # пул, признаки, обучение ранжирования, ~1 ч
python run.py submit --data data --art artifacts --method ens_all4 --out answer.csv
```

`train_dense.py` и `embed.py` сами используют GPU, если он есть. Базовая модель `intfloat/multilingual-e5-small` при первом запуске скачивается с HuggingFace, дальше всe работает офлайн.

### C. Dense-модель на внешнем GPU, остальное локально

Шаги 1-2 варианта B требуют GPU. Если своего нет, их можно выполнить в любом окружении с GPU, например в Google Colab:
- загрузить туда репозиторий и папку `data/`;
- выполнить `train_dense.py` и `embed.py` теми же командами;
- скачать `models/e5-ft/` и `artifacts/` обратно;
- шаги 3-4 (`run.py val` и `submit`) выполнить локально на CPU.

Код и параметры те же, что в варианте B.

### D. Без dense-модели

```bash
python run.py val --data data --art artifacts_nodense --no-dense
python run.py submit --data data --art artifacts_nodense --method ens_all4 --out answer_nodense.csv
```

Все работает на CPU за ~1 час. Recall ниже, ≈ 0.88: это оценка по версии без dense (v5, валидация 0.904) с учетом обычной разницы валидации и платформы в 0.024.

### О воспроизводимости
- LightGBM обучается с `seed=42, deterministic=True`. При одних и тех же эмбеддингах полный прогон `run.py val` + `submit` дает одинаковый `answer.csv`.
- Дообучение e5 на GPU не детерминировано (особенности CUDA). Поэтому варианты B и C дают очень близкий, но не обязательно идентичный ответ. Для точного воспроизведения загруженного файла - вариант A.
- Дообучение на CPU технически возможно (`train_dense.py` работает и без GPU), но занимает много часов.

## 2. Подход

Идея: пул из 16 каналов -> 4 LightGBM-модели в ансамбле. Полнота пула 0.981, итог 0.924 на валидации, 0.902 на платформе.

Поиск устроен в два шага:

1. Широкий пул (~1100 кандидатов на запрос). 16 каналов - пар «способ поиска * область». Каждый канал отдает свой top-K, в пуле их объединение. Полнота пула на валидации - 0.981.
2. Отбор 50 из пула. Ансамбль из четырех LightGBM-ранкеров (LambdaRank) по ~60 признакам. Итоговое место кандидата - это среднее перцентилей мест по всем моделям.

### 2.1 Данные и признаки: что и почему

В train нет `query_id`. Запросом считается группа строк с одинаковыми `search_*`, ее объявления - релевантные.

**Тексты.**
- Заголовок, параметры и описание объявления: стемминг Snowball, стоп-слова
- Длинное описание обрезается до 3000 символов, главное в начале
- Числа из параметров выброшены, для поиска шум

**Каналы пула и почему они такие:**

| Канал                                                                                   | Зачем                                                                                                                                                     |
|-----------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `bm25_*` - BM25F по полям: заголовок *3, история запросов *2, параметры *1, описание *1 | Точное совпадение слов. История запросов дописывает к объявлению запросы, по которым его выбирали: «Скупка б/у техники» находится по «скупка телевизоров» |
| `char_*` - char 3-5-граммы по заголовку                                                 | Опечатки и формы слов, которые не склеил стеммер                                                                                                          |
| `dense_*` - дообученная e5                                                              | Синонимы и смысл: «адвакат» - «юрист»                                                                                                                     |
| `mc_near`, `mc_remote` - подкатегория                                                   | Запросы без общих слов с объявлением: «укладка плитки» - «Ремонт квартир под ключ». Распределение подкатегорий берется по похожим запросам из истории     |
| `hist_*`, `locpop` - история выборов                                                    | Что выбирали по похожим запросам и из этой локации                                                                                                        |

**Области поиска.** Медианное расстояние до выбранного исполнителя  3 км, у 83% выборов локация совпадает с локацией поиска (из eda.py). Поэтому каждый канал ищет отдельно:
- `same` - та же `location_id`
- `near` - ближе 30 км, или локация, куда исторически обращаются пользователи этой локации
- `remote` - только удаленные и онлайн-услуги
- `all` - вся страна

Координат запроса нет. Центр локации поиска оценивается медианой координат объявлений этой локации, а если их нет, то медианой координат выбранных оттуда объявлений.

**Признаки ранжирования (~60):**
- **Текст:** скоры каналов, нормированные внутри запроса; BM25 по каждому полю отдельно; доля слов запроса в заголовке; доля слов фильтра запроса в параметрах объявления
- **Гео:** та же локация, расстояние, близость `exp(-d/30км)`, флаг удаленной услуги
- **Рубрика:** подкатегории для запроса
- **Каналы:** какие каналы нашли кандидата (бинарные) и в скольких он найден
- **Относительно соседей:** место кандидата внутри пула по каждому скору, отзывам, рейтингу, цене и расстоянию; отклонение от медианы пула
- **Запрос:** длина, максимальный BM25, число объявлений рядом
- **Фильтры:** рейтинг из фильтра запроса 

### 2.2 Модели и алгоритмы

| Компонент | Реализация                                                                                                                                      |
|---|-------------------------------------------------------------------------------------------------------------------------------------------------|
| BM25F | своя реализация на `scipy.sparse`                                                                                                               |
| Char n-grams, соседние запросы | `sklearn` TfidfVectorizer + косинус                                                                                                             |
| Dense | `intfloat/multilingual-e5-small`, дообученная на парах «запрос - выбранное объявление» (MultipleNegativesRankingLoss, 2 эпохи) `train_dense.py` |
| Ранжирование | LightGBM LambdaRank: 4 модели с разными признаками и гиперпараметрами, среднее перцентилей мест                                                 |
| Бейзлайны для сравнения | одиночные ретриверы; ретривер + гео; линейная комбинация признаков с весами, подобранными координатным спуском прямо по Recall@50               |

Все модели работают локально, без внешних API.

## 3. Как проверялось качество до отправки

**Валидация, похожая на бенчмарк** (`run.py val`, режимы в `cg/pipeline.py: make_split`). Пришлось устранить три перекоса, из-за которых ранняя валидация врала (см. раздел 4):

1. Запросы. 10 000 групп, по одной на текст запроса (`val_sampling=by_text`). В бенчмарке все запросы уникальны, и 63% из них не встречались в train. В случайной выборке групп таких было бы 13%, а с `by_text` 62%.
2. Корпус. Искомые объявления плюс случайные объявления из train, всего ~189 тыс., как в бенчмарке (`val_corpus=train_sample`). Искомые и остальные кандидаты одного происхождения, так что модель не может найти ответ по признакам «объявление из train».
3. История выборов остается только у 10% объявлений корпуса. В бенчмарке в train встречалось 9.6% объявлений.

Вся история (поле BM25, соседние запросы, популярность, пары для дообучения e5) строится без запросов валидации, утечки ответа нет.

**Честный замер.** Веса и модели подбираются на половине A запросов валидации, Recall@50 меряется на половине B. Отдельно считается полнота пула.

**Калибровка валидации по платформе:**

| Версия                    | Валидация | Платформа | Разница                            |
|---------------------------|---|---|------------------------------------|
| v2                        | 0.867 | 0.848 | 0.019                              |
| v3                        | 0.937 | 0.861 | 0.077 - перекос найден и исправлен |
| v4                        | 0.896 | 0.872 | 0.024                              |
| v6                        | 0.909 | 0.885 | 0.024                              |
| v7, `lgbm`                | 0.923 | 0.899 | 0.024                              |
| v7, `ens_all4` - **итог** | 0.924 | **0.902** | 0.022                              |

Начиная с v4, разница стабильна: 0.022–0.024. Поэтому улучшения выбирались по валидации, а на платформу отправлялись только версии, которые заметно лучше предыдущих.

**Диагностика** (`diagnose.py`, печатается автоматически после построения пула):
- вклад каждого канала: полнота в одиночку и уникальная доля
- почему упущенные объявления не попали в пул
- кривые полноты top-K по каждому ретриверу
- примеры промахов

**Сравнение подходов** (Recall@50 на валидации):

| Метод | v4 | v7 |
|---|---|---|
| только BM25 | 0.381 | — |
| только char n-grams | 0.273 | — |
| только история | 0.064 | — |
| BM25 + гео | 0.791 | — |
| char + гео | 0.673 | — |
| линейная комбинация (веса по Recall@50) | 0.825 | — |
| LightGBM LambdaRank | 0.895 | 0.923 |
| ансамбль 4 × LightGBM (`ens_all4`) — **итог** | — | **0.924** |

Без гео любой текстовый метод даёт меньше 0.4, пользователь выбирает исполнителя рядом.

## 4. Найденные ошибки и что с ними сделано

| # | Что обнаружено                                                                                                          | Как нашел                                   | Что сделано                                                                       | Эффект                                          |
|---|-------------------------------------------------------------------------------------------------------------------------|---------------------------------------------|-----------------------------------------------------------------------------------|-------------------------------------------------|
| 1 | Пул ловил только 64.5%, ранжирование упиралось в этот потолок                                                           | полнота пула                                | Каналы «ретривер * область» вместо одного общего топа                             | пул 0.645 -> 0.952, итог 0.60 -> 0.87           |
| 2 | Удаленные услуги попадали в «рядом» и вытесняли местных                                                                 | диагностика каналов                         | Отдельная область `remote`, в `near` удаленных нет                                | входит в п. 1                                   |
| 3 | `search_location_id` бывает регионом без своих объявлений, тогда гео не работало                                        | промахи с `geo_ok=0`                        | Центр региона и affinity локаций по истории выборов                               | входит в п. 1                                   |
| 4 | Нет общих слов с запросом («укладка плитки» - «Ремонт квартир»)                                                         | «нет общих слов» в диагностике              | Каналы по подкатегории, затем дообученная e5                                      | доля таких промахов 1.1% -> 0.4% метрики        |
| 5 | Валидация завышала на 0.077 (v3): в ней частые запросы, а в бенчмарке длинный хвост                                     | `check_shift.py`: частота текстов запросов  | `val_sampling=by_text`                                                            | разница с платформой стабилизировалась на 0.024 |
| 6 | Объявления train отличимы от объявлений бенчмарка (AUC 0.69), в v3 модель могла учиться на происхождении                | `check_shift.py`: классификатор train/bench | `val_corpus=train_sample`                                                         | входит в п. 5                                   |
| 7 | У 42% искомых объявлений валидации была история выборов, а в бенчмарке у ~10%. Модель переоценивала признаки истории    | сравнение долей                             | История остается у 10% объявлений; модели без признаков истории в ансамбле        | входит в п. 5                                   |
| 8 | Сотни похожих исполнителей в пуле, трудно выбрать одного                                                                | анализ промахов ранжирования                | Признаки «относительно соседей», BM25 по полям, ансамбль                          | +0.013 на валидации (v4 -> v6)                  |
| 9 | Технические: координаты в parquet `decimal.Decimal`; `to_csv` на Windows пишет `\r\n`, и `\r` прилипает к последнему id | падения, проверка файла                     | Приведение к `float64`; `lineterminator="\n"`; проверка формата перед сохранением | —                                               |

**Что осталось:** 1.9% метрики теряется в пуле, в основном из-за странных выборов вроде «лагерь» → «ЛФК детям» или исполнителей за сотни км. Ещё ~5.7% теряется на выборе 50 из ~1100 похожих кандидатов.

## 5. Структура

```
run.py              точка входа, val (пул + ранжирование + сравнение) и submit
train_dense.py      дообучение e5 на парах «запрос - объявление»
embed.py            эмбеддинги корпуса дообученной моделью
cg/data.py          загрузка, группы-запросы, корпус
cg/pipeline.py      разбиение валидации (make_split), сборка пайплайна, проверка формата answer.csv
cg/retrievers.py    BM25F, char TF-IDF, история, dense
cg/pool.py          каналы пула, гео, признаки
cg/models.py        Recall@50, линейный тюнинг, LightGBM, ансамбли
cg/text.py          нормализация и стемминг
cg/dense_text.py    текст объявления для e5 (одинаковый при обучении и поиске)
eda.py              анализ данных
check_shift.py      проверка сдвига между валидацией и бенчмарком
diagnose.py         диагностика промахов пула
```
