# Кандидатогенерация для поиска услуг Авито (Recall@50)

## Идея решения

Задача — не упустить нужное объявление. Поэтому решение двухшаговое:

1. **Пул кандидатов (~500–1500 на запрос).** Несколько независимых ретриверов,
   каждый отдаёт top-150 по всей стране и top-150 «рядом» с пользователем.
   Объединение — пул. Его полнота — потолок для любого метода отбора.
2. **Отбор 50 из пула.** Сравниваем несколько способов: от одиночного BM25 до
   гибридной линейной формулы и LightGBM-ранкера.

Главное наблюдение, заложенное в дизайн: **услуги локальны**. Текстовый поиск по
всей стране вернёт 50 «автоподборов» из разных городов, и нужного среди них не будет.
Поэтому гео — отдельный канал отбора и ключевой признак (проверить на реальных
данных: `python eda.py` печатает долю совпадений локации и распределение расстояний).

### Ретриверы (шаг 1)

| Ретривер | Что ловит |
|---|---|
| **BM25F** (своя реализация на `scipy.sparse`): заголовок ×3, история запросов ×2, параметры ×1, описание ×1 | Точные совпадения слов. Стемминг Snowball склеивает словоформы |
| **История запросов (doc2query из логов)** — поле BM25 | К объявлению дописаны запросы, по которым его выбирали в train. «Скупка б/у техники» находится по «скупка телевизоров» |
| **Char n-gram TF-IDF** по заголовку | Опечатки, слитное/раздельное написание |
| **Query-neighbours** (коллаборативный) | Похожие запросы из train → что по ним выбирали. Заодно даёт prior подкатегории (microcat) |
| **Dense e5** (опционально) | Синонимы и семантика («обзвон по базе» ≈ «холодные звонки») |

### Признаки кандидата

Скоры ретриверов (нормированы в запросе), `same_loc`, `geo_prox`, `log_dist`,
`remote` (онлайн/удалённо), `is_delivery`, покрытие слов запроса заголовком,
покрытие фильтра запроса параметрами объявления, `rating_ok` (фильтр по рейтингу),
prior подкатегории, рейтинг и число отзывов.

Координат запроса нет — центр локации поиска оцениваем медианой координат объявлений
с тем же `location_id`.

### Сравниваемые методы (шаг 2)

| Метод | Описание |
|---|---|
| `bm25_only`, `char_only`, `hist_only`, `dense_only` | Бейзлайны: один ретривер, без гео |
| `bm25_geo`, `char_geo`, `dense_geo` | Ретривер + гео-признаки, веса подобраны |
| `hybrid_linear` | Все признаки, веса подобраны координатным спуском **прямо по Recall@50** |
| `lgbm` | LightGBM LambdaRank по всем признакам |

### v2: что поменялось в пуле (после первого прогона: pool recall 0.645, lgbm 0.600)

* Каналы «ретривер × область» (`DEFAULT_CHANNELS` в `cg/pool.py`): all / same / near / remote.
  В v1 удалённые услуги считались «рядом» и вытесняли местных исполнителей.
* Loc affinity: P(локация объявления | локация поиска) по истории + центр локации поиска
  по истории (если search_location_id — регион без своих объявлений).
* Нетекстовые каналы: `mc_near` (подкатегория похожих запросов рядом), `locpop`
  (что чаще выбирали из этой локации).
* Новые признаки: `aff`, `item_pop`, `pop_loc`, `n_src`.
* `diagnose.py` — почему упущенные объявления не попали в пул, вклад каждого канала,
  кривые полноты top-K по каждому ретриверу.

### v3: валидация «как бенчмарк» + признаки для ранжирования (после v2: пул 0.952, lgbm 0.867)

* Искомые объявления валидации в v2 имели историю выборов в 42% случаев, а в корпусе
  бенчмарка — только ~10%. Теперь у 90% из них история стирается (`val_warm_rate`),
  а поиск идёт по корпусу размером с бенчмарк (`val_corpus=bench`).
* Признаки: какой канал нашёл кандидата (`ch_*`), ранги внутри пула (`r_*`),
  признаки запроса (`q_*`). Вариант `lgbm_nohist` — без признаков истории.

### v4: валидация, похожая на бенчмарк (реальный скор 0.872, валидация 0.896)

`check_shift.py` показал: запросы бенчмарка уникальны, 63% не встречались в train
(в случайной валидации — 13%); объявления train отличимы от объявлений бенчмарка (AUC 0.69).
Поэтому по умолчанию: `val_sampling=by_text` (одна группа на текст запроса) и
`val_corpus=train_sample` (искомые и прочие кандидаты — из train, ~190k, история у 10% объявлений).

### v5: ранжирование
BM25 по полям отдельно (`bm25f_*`); `lgbm_big` (все негативы, 127 листьев, lr 0.03);
ансамбли `ens_nohist`, `ens_all` — среднее перцентилей мест внутри запроса.

### v6: пул шире + признаки «относительно соседей» + dense (опционально)
* Каналы: `bm25_all` 300, `char_all` 100, `mc_near` 300, новый `mc_remote` (удалённые услуги
  по подкатегории).
* Признаки: места кандидата в пуле по отзывам/рейтингу/цене/BM25 заголовка (`r_*`),
  отклонение от медианы пула (`d_*`).
* Dense: `embed.py --titles-only --max-seq 32` (multilingual-e5-small, CPU ~20–40 мин).

### v7: дообученный e5 (Kaggle GPU)
1. `python make_ft_data.py --data data --out kaggle_upload` — пары для обучения берутся тем же
   разбиением, что и валидация (`make_split`): без запросов валидации и только «тёплые» объявления.
2. На Kaggle: датасет из `kaggle_upload/`, ноутбук `kaggle/finetune_e5.ipynb`, GPU → `result.zip`.
3. Распаковать: `e5-ft/` → `models/e5-ft/`, `emb_*` → `artifacts_v7/`; `python run.py val --art artifacts_v7`.
Модель лежит в проекте — решение воспроизводится без интернета.

## Валидация

В train нет `query_id`, поэтому запрос = группа строк с одинаковыми `search_*`.
Откладываем 6000 групп. Вся «история» (поле qhist, query-neighbours, обучение e5)
строится **без** отложенных групп — иначе утечка ответа.
Корпус валидации = объявления бенчмарка ∪ объявления train.
Веса и модели подбираются на половине A отложенных запросов, метрика — на половине B.

## Запуск

```bash
pip install -r requirements.txt
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в data/

python eda.py --data data                      # статистика: гео, пересечения, фильтры
python run.py val --data data                  # сравнение методов -> artifacts/results.csv
python run.py submit --data data --method lgbm # -> answer.csv (с проверкой формата)
```

Повторный тюнинг без пересборки пула: `python run.py val --data data --reuse-pool`.

**Dense (опционально, лучше с GPU):**
```bash
pip install sentence-transformers torch
python embed.py --data data --art artifacts_v6 --titles-only --max-seq 32   # эмбеддинги (CPU)
python train_dense.py --data data --out models/e5-ft                 # дообучение (по желанию)
python embed.py --data data --model models/e5-ft
python run.py val --data data                                        # dense подхватится сам
```

Ориентир по ресурсам: ~160k объявлений — 2 мин и 1.6 ГБ RAM на 2 ядрах (без dense).
На полном корпусе (~450k) ожидаю 20–40 мин на `val` и 4–6 ГБ RAM.

## План улучшений лучшего метода

1. Подобрать `k_global` / `k_local` / `local_radius_km` в `cg/pipeline.py` по полноте пула.
2. Дообучить e5 (`train_dense.py`) — обычно самый большой прирост на коротких запросах.
3. Добавить в LightGBM ранги внутри ретриверов и взаимодействия «удалённая услуга × расстояние».
4. Лемматизация (pymorphy3) вместо стемминга, веса полей BM25.

## Использованные open-source библиотеки

pandas, numpy, scipy, scikit-learn (TF-IDF), PyStemmer (Snowball), LightGBM,
опционально sentence-transformers + модель `intfloat/multilingual-e5-small` (MIT).
Все работают локально, внешних API нет.
